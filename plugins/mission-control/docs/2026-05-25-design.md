# `mission-control` plugin — design

## Overview

A Claude Code plugin that lets a **Mission Control session** (the central coordinator) run a strict-turn-taking conversation with **N project sessions** (the "Astronauts") running in different directories on the same machine.

The plugin's contribution is the *protocol* — a small, fail-loud state machine that uses Unix PIDs as turn-handoff semaphores and markdown files as the message payload. Each peer pair is isolated: a stuck channel in one pair doesn't affect any other. A single skill (`FlightDirector`) loaded into both sides handles the runtime — diagnosing state on every invocation, picking the right next action, executing.

### What this is NOT

- Not a daemon. There is no long-running coordinator process.
- Not MCP. (MCP would be the standard answer for this; the plugin deliberately picks a lighter-weight pure-shell pattern because the protocol's payload is markdown-first by design and MCP's JSON-RPC-over-stdio feels out-of-place. MCP remains the documented escape hatch if the protocol's failure modes prove harder than expected.)
- Not cross-machine. PID kills are local; this is single-user single-machine only.
- Not event-driven in the polling sense. The kernel's `wait $PID` returning is the event source; Claude Code's auto-notify-on-background-bash-completion is the glue.

### Motivating requirements (the two things polling can't do cleanly)

1. **Turn-taking semantics.** One peer speaks, the other responds, repeat. The previous polling-based design (the retired `mindmap-channel` plugin) allowed both sides to write concurrently, which was chaotic.
2. **Multi-project orchestration.** One Mission Control talking to N project sessions concurrently, with each pair isolated from the others.

Latency and setup ergonomics were *not* motivators (current polling design is fast enough; manual symlink setup is acceptable). This is a turn-taking + fanout protocol, not a low-latency messaging system.

## Architecture

### Three layers

| Layer | What it is | Owns |
|---|---|---|
| **Protocol** | 4 slash commands + 1 skill (FlightDirector) | What Claude executes per turn / per user command |
| **Process** | `sleep infinity` PIDs as turn semaphores | Cross-session "your turn" signal via kernel `wait` |
| **Filesystem** | `to-/from-` message files + `state.json` per pair | Audit trail, message payloads, handshake metadata |

### Per-pair isolation

Each `(Mission Control, peer)` pair has its own state directory at `${MISSION_CONTROL_ROOT:-$HOME/.mission-control}/<peer>/`. The directory's existence *is* the pair's existence. No global daemon, no global state, no shared blast-radius.

```
${MISSION_CONTROL_ROOT:-$HOME/.mission-control}/
├── orbital/
│   ├── state.json              # current_pid, current_uuid, seq, last_read_seq
│   ├── to-Orbital.md           # canonical outbound (Mission Control → orbital)
│   └── from-Orbital.md         # symlink to peer's outbound
├── kimmy/
│   └── (same shape)
├── c-f-a/
│   └── (same shape)
└── .archive/
    └── 2026-05-25T18-42-00Z/   # snapshots from prior mission-complete invocations
        └── orbital/
            └── (preserved state + logs)
```

### Plugin location

The plugin ships in the **orbital marketplace** as a peer of `shifting`, `scaffolding`, `trajectory`, `telemetry`. Adopters pull it via standard marketplace install + a version bump.

The decision to ship from orbital (rather than spinning up a future mindmap-marketplace) is pragmatic — orbital is already a marketplace, mindmap-marketplace doesn't exist yet, and this plugin is meta enough to fit alongside the formal-reasoning plugins. If the mindmap-marketplace ever stands up, mission-control can migrate there with a `git mv` that preserves history.

    ├── kill-pid.sh                 # kills peer's PID with UUID-check + ps-command-check defense
    ├── append-message.sh           # appends a seq-numbered timestamped block to to-<Peer>.md

    └── test/                       # unit smoke tests for each script (see Testing)

### Commands (4 total, the user-visible surface)

#### `/mission-control:initialize <peer>`

**Mission Control side only.** Bootstraps a new pair.

1. `mkdir ${MISSION_CONTROL_ROOT:-$HOME/.mission-control}/<peer>/`
2. Write initial `state.json`: `{channel: "<peer>", self: "MissionControl", peer: "<Peer>", seq: 0, our_pid: null, last_read_seq: -1}`
3. Create `to-<Peer>.md` with channel header.
4. Symlink the plugin's `commands/launch-sequence.md` into `<peer-project-root>/.claude/commands/mission-control:launch-sequence.md` (so the peer can invoke the command without installing the plugin separately).
5. Append the operator's initial message to `to-<Peer>.md` (block carries `seq=0, intent=handshake-init`, plus a new PID+UUID).
6. Spawn `sleep infinity` → record PID + UUID in `state.json`.
7. Spawn the wait-bash in background via Claude Code's Bash tool with `run_in_background: true`:
   ```bash
   wait <our-pid> ; echo "channel=<peer> event=peer-spoke"
   ```
8. Invoke the Skill tool to load `mission-control:FlightDirector`.
9. Return a one-line instruction the operator pastes into the peer's Claude Code session:
   > "Run `/mission-control:launch-sequence` in your peer Claude Code session to complete the handshake."

#### `/mission-control:launch-sequence`

**Peer side only.** Completes the handshake.

1. Create `<peer-project>/thoughts/to-MissionControl.md` with channel header.
2. Symlink `<peer-project>/thoughts/to-MissionControl.md` → `${MISSION_CONTROL_ROOT:-$HOME/.mission-control}/<peer>/from-<Peer>.md`.
3. Read `<peer-project>/thoughts/from-MissionControl.md` (the symlink that `initialize` set up, pointing at Mission Control's `to-<Peer>.md`) — find `seq=0` handshake block.
4. Perform whatever initial actions the handshake message asked for.
5. Append response block to `to-MissionControl.md` (`seq=0, intent=handshake-ack`, plus our new PID+UUID).
6. Spawn `sleep infinity` → record PID + UUID in peer's own local state file.
7. Spawn the wait-bash in background with `run_in_background: true`.
8. Validate Mission Control's PID UUID matches what `${MISSION_CONTROL_ROOT:-$HOME/.mission-control}/<peer>/state.json` says.
9. `kill <Mission-Control-pid>` → Mission Control's wait returns; Mission Control's Claude gets the auto-notification.
10. Invoke the Skill tool to load `mission-control:FlightDirector`.

#### `/mission-control:mission-status`

**Either side.** Read-only diagnostic. Iterates all pairs in `.mission-control/`, runs `diagnose-state.sh` on each, formats a table:

```
Channel       | State          | Our PID  | Peer PID | Last seq | Last activity        | Suggested action
--------------|----------------|----------|----------|----------|----------------------|------------------
orbital       | healthy        | 48291    | 48317    | 7        | 2026-05-25T18:42:00Z | waiting on peer
kimmy         | peer-crashed   | 48422    | (dead)   | 12       | 2026-05-25T14:30:00Z | resync (peer's PID is dead)
c-f-a         | not init       | -        | -        | -        | -                    | initialize
```

No state changes. Just reads + reports.

#### `/mission-control:end-mission [--purge]`

**Mission Control side only.** Global teardown of all pairs.

Default mode: archive. Move every active pair into `.mission-control/.archive/<UTC-timestamp>/`. Logs preserved.

`--purge`: delete everything. Use to clear accumulated archive cruft.

Best-effort: each pair's local PIDs are killed (UUID-checked); peer-side symlinks are left alone (the peer will notice the broken symlink on its next session). No peer-side cleanup is performed because mission-complete may be invoked because peers are dead.

### Skill: `FlightDirector` (the runtime intelligence)

`SKILL.md` describes the state machine. The skill is loaded on BOTH sides during their respective bootstrap commands (`initialize` for Mission Control, `launch-sequence` for peers). Once loaded, it directs Claude's behavior for the rest of the session.

**Invocation contexts:**

1. **Notification-triggered.** A background bash completes with stdout `channel=<peer> event=peer-spoke`. Claude sees this notification, recognizes the FlightDirector loaded skill applies, dispatches to the `<peer>` channel.
2. **User-triggered.** The user types something like "FlightDirector, what's the status of orbital?" or "FlightDirector, resync kimmy." The skill's loaded instructions tell Claude to invoke its dispatch logic.
3. **Command-triggered.** The slash commands (`mission-status`, `end-mission`) invoke the skill internally for their work.

**Dispatch logic (every invocation):**

```
1. Identify which peer this is about:
   - Notification: parse channel=<peer> from notification stdout
   - User-invoked: peer from chat context (or "all" for global)

2. Run diagnose-state.sh on the channel state dir.

3. Map (state model × invocation intent) → next action via the matrix below.

4. Execute. Update state.json atomically (write-then-rename).
```

**State-diagnosis matrix:**

| Diagnosed state | Invocation context | Action |
|---|---|---|
| State present, healthy, peer-spoke notification | notification | Take turn (read since last_read_seq, act, append response, spawn new PID, kill peer's prior PID) |
| State present, healthy, our turn already done, no notification | user-invoked status | Report: "waiting on peer" |
| State present, healthy, our turn pending, no notification yet | user-invoked anything | Report: "peer hasn't spoken yet" (wait) |
| State missing | user-invoked initialize | Run initialize command logic |
| State missing | user-invoked anything else | Halt: "no channel for <peer>; run /mission-control:initialize <peer>" |
| State present, our_pid dead, peer's PID alive | any | Halt: "our PID died unexpectedly; suggest resync or end-mission" |
| State present, our_pid alive, peer's PID dead | any | Halt: "peer crashed; suggest resync or end-mission" |
| State present, both PIDs dead | any | Halt: "channel stale; suggest resync or end-mission" |
| State present, UUID mismatch | any | Halt: "state corrupt; suggest resync (with diagnosis)" |
| State present, symlink dangling | any | Halt: "peer's outbound symlink is broken; suggest resync" |
| User intent = "end mission" | any | Run end-mission command logic |
| User intent = "resync <peer>" | any | Tear down + re-initialize the named pair |
| User intent = "close <peer>" / "splashdown <peer>" | any | Graceful close of one pair (send final block, archive state, leave peer's symlinks) |

Every row has a defined action. No silent corruption. Halt-loud-with-attribution is the default for unhealthy states.

### Scripts (the bash primitives)

Each script is POSIX-portable (works on macOS bash 3.2 + Linux bash 5.x without OS-branching). Cross-platform discipline:

- Use `wc -c` (not `stat -c %s` / `stat -f %z`).
- Use `find -L "$F" -newer "$M" -print` (not `[ "$F" -nt "$M" ]` which has subtle symlink semantics).
- Use `touch -r "$F" "$M"` for clock-skew-safe marker updates (supported on both BSD and GNU `touch`).
- Use `jq` for JSON read/write (declared as a plugin dependency; degrade gracefully if absent — silent fail-open).

**`diagnose-state.sh <peer>`** — outputs JSON:

```json
{
  "channel": "orbital",
  "state_exists": true,
  "state_parses": true,
  "our_pid_alive": true,
  "our_pid_uuid_ok": true,
  "their_pid_alive": false,
  "their_pid_uuid_ok": null,
  "symlinks_intact": true,
  "last_seq_in": 7,
  "last_seq_out": 8,
  "diagnosis": "peer-crashed",
  "suggested_action": "resync"
}
```

**`new-pid.sh`** — spawns `sleep infinity &`, generates UUID via `uuidgen` (Linux) or `dd if=/dev/random` fallback, writes both to state.json atomically.

**`kill-pid.sh <pid> <uuid> <peer-state-path>`** — validates UUID match + `ps -p $pid -o command= | grep -q "sleep infinity"`. Both must pass or refuses. Halts loud on mismatch.

**`append-message.sh <peer> <intent> <body-or-stdin>`** — appends a seq-numbered timestamped block to `to-<Peer>.md`. Block header carries `seq=N intent=X pid=Y uuid=Z`. Block body is free-form markdown.

**`read-since-seq.sh <peer>`** — parses `from-<Peer>.md`, returns blocks with `seq > last_read_seq`. Uses `awk` to split on `## [...] seq=N` headers; robust to file restructuring.

## Data flow

### Phase 1 — Initialization (Mission Control side)

```
User: /mission-control:initialize orbital

initialize.md does:
  ├── mkdir .mission-control/orbital/
  ├── write state.json (seq=0, no PIDs yet)
  ├── append handshake-init block to to-Orbital.md (operator's initial message)
  ├── symlink commands/launch-sequence.md → orbital/.claude/commands/mission-control:launch-sequence.md
  ├── new-pid.sh → m-pid-0, m-uuid-0; written into state.json
  ├── update last block in to-Orbital.md with m-pid-0 + m-uuid-0 (so peer can kill it)
  ├── spawn `wait m-pid-0 ; echo "channel=orbital event=peer-spoke"` as background bash
  ├── invoke Skill tool to load FlightDirector
  └── return: "Run /mission-control:launch-sequence in orbital."
```

### Phase 2 — Launch sequence (peer side, in orbital's session)

```
User: /mission-control:launch-sequence

launch-sequence.md does:
  ├── write orbital/thoughts/to-MissionControl.md with channel header
  ├── symlink orbital/thoughts/to-MissionControl.md
  │            → ${MISSION_CONTROL_ROOT:-$HOME/.mission-control}/orbital/from-Orbital.md
  ├── read-since-seq.sh on from-MissionControl.md (already symlinked from initialize)
  │   → finds seq=0 handshake-init + m-pid-0 + m-uuid-0
  ├── perform initial actions (per the handshake message body)
  ├── new-pid.sh → o-pid-0, o-uuid-0; written into orbital's local state file
  ├── append-message.sh handshake-ack + o-pid-0 + o-uuid-0 → to-MissionControl.md
  ├── spawn `wait o-pid-0 ; echo "channel=mindmap event=peer-spoke"` as background bash
  ├── kill-pid.sh m-pid-0 m-uuid-0 → Mission Control's wait returns; Mission Control's Claude is notified
  └── invoke Skill tool to load FlightDirector
```

### Phase 3 — Steady-state turn cycle

FlightDirector loaded on both sides. On each peer-spoke notification:

```
1. Parse channel=<peer> from notification stdout.
2. diagnose-state.sh <peer> → state model JSON.
3. If state healthy + peer-spoke:
   a. read-since-seq.sh → new blocks since last_read_seq
   b. extract peer's new PID + UUID from latest block
   c. ACT on the new content (Claude's actual reasoning, per intent)
   d. new-pid.sh → my new PID + UUID
   e. update state.json (seq++, our_pid = new PID, last_read_seq = peer's seq)
   f. append-message.sh response + my new PID + UUID
   g. spawn `wait <my-new-pid> ; echo "channel=<peer> event=peer-spoke"` as background bash
   h. kill-pid.sh <peer-old-pid> <peer-old-uuid> → peer's wait returns
4. Else: halt-loud per the state-diagnosis matrix.
```

Step 3c is the only step that requires LLM reasoning; everything else is mechanical.

### Phase 4 — Multi-project fanout

Mission Control has N pairs active:

```
${MISSION_CONTROL_ROOT:-$HOME/.mission-control}/
├── orbital/    (m-pid-N alive, waiting)
├── kimmy/      (m-pid-K alive, waiting)
└── c-f-a/      (m-pid-C alive, waiting)
```

Each pair has its own background `wait` running. The `echo "channel=<peer>"` line each `wait` prints disambiguates notifications. When orbital's peer kills `m-pid-N`, the corresponding wait completes and Claude's notification carries `channel=orbital`. FlightDirector's dispatch routes to the orbital channel's state dir.

Two peers killing simultaneously = two notifications in quick succession. FlightDirector handles them in order. Each pair's state is isolated; no cross-pair corruption.

### Phase 5 — Teardown

Per-pair (graceful, peer alive):
```
User: "FlightDirector, splashdown orbital."
→ append-message.sh splashdown intent → to-Orbital.md
→ wait briefly for peer ack (or timeout)
→ kill-pid.sh our_pid (our own)
→ mv .mission-control/orbital/ .mission-control/.archive/<ts>/orbital/
```

Global (no peer ack needed):
```
User: /mission-control:end-mission
→ for each pair_dir:
    - kill-pid.sh our_pid (best-effort; UUID-checked)
    - kill-pid.sh peer's last-known PID (best-effort; UUID-checked)
    - mv pair_dir into .archive/<ts>/
```

`--purge` skips the archive and `rm -rf`s.

## Error handling

### Five load-bearing failure modes

#### 1. Peer crashes mid-turn

**Detection:** `diagnose-state.sh` flags `their_pid_alive: false` after our turn completed and peer should have responded.
**Mitigation (v1):** `mission-status` reports it; user invokes resync via natural language ("FlightDirector, resync orbital").
**Mitigation (v2 candidate):** Heartbeat — each side appends `seq=N intent=heartbeat` block every N minutes; missed heartbeats trigger auto-diagnosis. Deferred to v2 to avoid log noise in v1.

#### 2. PID recycling

**Detection:** UUID stored alongside PID; before any `kill`, the script validates `actual_uuid == expected_uuid`.
**Mitigation (load-bearing):** `kill-pid.sh` performs TWO checks before killing:
- UUID match against state.json
- `ps -p $pid -o command= | grep -q "sleep infinity"`

Either failing = halt loud, do not kill. This defeats both recycled-PID and rogue-process cases.

#### 3. State.json corruption / concurrent writes

**Mitigation:** Atomic writes via `mv` (POSIX rename is atomic). The pattern:

```bash
jq '...' state.json > state.json.tmp
mv state.json.tmp state.json
```

Parse failures → halt loud, suggest resync.

#### 4. Broken symlink / missing files

**Detection:** `[ -e <path> ]` follows symlinks; returns false on dangling links. Every script reading from-X.md does this check first.
**Mitigation:** Missing file → halt loud + suggest resync. No silent fabrication.

#### 5. Duplicate initialize / orphan PIDs

**Detection:** `initialize <peer>` checks if `.mission-control/<peer>/state.json` already exists. If yes: refuse, suggest resync or end-mission.
**Orphan cleanup:** Manual via `end-mission --purge` or per-pair `resync`. No auto-cleanup on SessionEnd (per operator preference — explicit teardown control).

### Halt-loud-with-attribution discipline

Every error path includes:
- The failing condition (UUID mismatch, dangling symlink, parse error, …)
- The script/section responsible for the contract (`scripts/kill-pid.sh §UUID-check`)
- A user-actionable recovery hint (`/mission-control:mission-status` or "FlightDirector, resync <peer>")

No silent corruption. No "try harder" retry loops. Failures surface immediately with next-step direction.

## Testing

### Three layers

#### Layer 1: Unit smoke tests for scripts (ships with v1)

Location: `plugins/mission-control/scripts/test/`. Each script gets a `test_<script>.sh` that:
- Mocks the filesystem state with a temp dir
- Invokes the script
- `diff`s output JSON / state.json mutation against expected fixture
- Asserts exit codes

Covered scripts: `diagnose-state.sh`, `new-pid.sh`, `kill-pid.sh` (especially UUID-mismatch path), `append-message.sh`, `read-since-seq.sh`. Pure-bash test harness; no `bats` dependency.

#### Layer 2: One-sided integration (ships with v1)

Location: `plugins/mission-control/scripts/test/integration/`. A scripted scenario simulating a peer's actions via direct file writes + `kill` calls. Mission Control's commands are real; peer is mocked. Validates FlightDirector's state-machine logic end-to-end without needing two real Claude sessions.

#### Layer 3: Manual two-session integration (ships as checklist)

Location: `plugins/mission-control/docs/manual-test-checklist.md`. Steps the operator follows once to exercise the real notification mechanism (which can't be faked without actually running two Claude Code sessions). Checklist covers: initialize → launch-sequence → 3 turns of round-trip → mission-status → end-mission → re-initialize after archive.

## Open questions + known limitations

### Limitations (accepted for v1)

1. **No heartbeat.** Silent peer-crash hangs are user-detected via `mission-status`. v2 candidate.
2. **Single-machine only.** PID kills don't traverse machines. v2 candidate (would require MCP transport).
3. **No auto-teardown on SessionEnd.** Operator-preferred — explicit teardown control. Trade-off: orphan PIDs across session crashes need manual cleanup.
4. **The `mindmap-channel` plugin in orbital's tree is retired.** Its work is superseded by `mission-control`. The directory `plugins/mindmap-channel/` should be deleted (or moved to `thoughts/archive/`) before mission-control is registered in marketplace.json.

### Open questions for implementation phase (writing-plans skill)

1. **Hooks?** Whether the plugin needs hooks beyond what's described. Candidate: a PostToolUse hook on Bash that detects background-bash completion and surfaces it to FlightDirector if the stdout matches `channel=... event=peer-spoke`. Maybe redundant with Claude Code's native auto-notify; leave for implementation phase to determine.
2. **Exact marker file location and naming for the peer side.** Mission Control state is at `${MISSION_CONTROL_ROOT:-$HOME/.mission-control}/<peer>/`. Peer-side state — where does that live? Proposed: `<peer-project>/thoughts/.mission-control-state.json` (one file, not a directory, since each peer has at most one channel to Mission Control). Validate during implementation.
3. **UUID generation.** `uuidgen` is on macOS by default; on Linux it's in `uuid-runtime`. Fallback to `dd if=/dev/urandom bs=16 count=1 | hexdump -e '"%02x"' | head -c 16` if absent. Decide which path is default during implementation.
4. **jq dependency.** Declared as a plugin dependency. Fail-open behavior when absent matches the orbital marketplace's existing convention (`mindmap-channel` did the same). Validate during implementation.

### Five questions worth resolving (priority order)

1. **(Load-bearing) Background-bash auto-notify reliability.** The protocol
   assumes that when the peer kills our `sleep infinity` PID, the orbital
   session's background `wait $PID; echo "channel=<peer> event=peer-spoke"`
   completes, and Claude sees the notification and dispatches FlightDirector.
   Claude Code's Bash tool with `run_in_background: true` does emit completion
   notifications, but it is not empirically verified that Claude reliably
   *pattern-matches* on stdout content like `channel=orbital event=peer-spoke`
   to trigger a skill dispatch (versus surfacing the notification passively
   for the user to act on). A ~10-minute smoke test (`sleep 5; echo "channel=test
   event=peer-spoke"` as a background bash, observe whether Claude
   auto-dispatches) is the cleanest first move once the plugin is installed.

2. **Initial-message-content path is undefined.** Step 5 of `initialize.md`
   says *"Append the operator's initial message to `to-Orbital.md`."* How
   does the operator's message content arrive? Three plausible paths:
   - Slash-command argument: `/mission-control:initialize orbital "<message>"`
   - The skill prompts the operator interactively after `initialize` starts
   - A separate `send-initial-message.sh` script the user invokes pre-init

   Spec picks none. `writing-plans` should commit to one (recommend the
   slash-command-argument path — most explicit, least state).

3. **Symlinked launch-sequence command + `${CLAUDE_PLUGIN_ROOT}` resolution.**
   Step 4 of `initialize.md` symlinks `commands/launch-sequence.md` from the
   Mission Control's plugin cache into the peer-project's `.claude/commands/`. The
   spec claims this lets the peer invoke the command without installing the
   plugin separately. But if the launch-sequence command file uses
   `${CLAUDE_PLUGIN_ROOT}` (Claude Code convention) to find its scripts, that
   variable resolves to Mission Control's plugin cache — which the peer's
   session can't reach.

   Two resolutions: (a) the command file uses absolute paths only (no
   `${CLAUDE_PLUGIN_ROOT}`), and the symlink works; (b) the peer must also
   enable the plugin (which negates the "without installing" claim). The
   spec needs to pick one. (Recommend (b) — the peer has to pull the
   plugin anyway to get FlightDirector, so requiring the plugin be enabled
   is honest about the dependency.)

4. **`end-mission` mid-turn semantics.** If Mission Control runs
   `/mission-control:end-mission` while a turn is in flight (we've sent,
   peer is processing, peer hasn't killed our PID yet), the teardown
   kills our own PID. The peer's `wait` returns `peer-spoke` — but
   there's no actual new message; we just left. The dispatch matrix has
   rows for "our_pid alive, peer's PID dead" but no explicit row for
   "peer-spoke notification with no new content." Probably falls into
   "state corrupt" → halt loud, but making this explicit (or emitting a
   `seq=N intent=farewell` block before killing during teardown so the
   peer sees a clean shutdown signal) is cleaner.

5. **Slash-command-triggers-skill-load.** Steps 8 and 10 of `initialize`
   and `launch-sequence` say *"Invoke the Skill tool to load
   `mission-control:FlightDirector`."* Slash commands run as prompts to
   Claude, who then takes actions. Probably a slash-command instruction
   can reliably trigger Skill loading, but worth confirming. If not, the
   user must manually `/skills mission-control:FlightDirector` after each
   bootstrap — acceptable, but should be documented in the README.

### Secondary concerns (worth flagging, not blocking)

- **State.json schema versioning.** Adding `schema_version: 1` now is cheap
  insurance against v2's heartbeat / timestamp additions breaking older
  readers.

- **`ps`-command grep portability.** `ps -p $pid -o command= | grep -q "sleep
  infinity"` works on Mac and most Linuxes, but on systems where the binary
  shows as `/bin/sleep infinity` the substring `"sleep infinity"` still
  matches — verify during implementation.

- **`mission-status` per-pair fault isolation.** If pair K's `state.json` is corrupt,
  `mission-status` should print partial table with K's row marked corrupt rather than
  halting the entire mission-status command. Spec doesn't say which.

- **Natural-language vs slash-command for resync/splashdown.** If
  *"FlightDirector, resync orbital"* is the canonical recovery path, the
  skill's intent parser needs robust variations (`sync`, `re-sync`, `restart
  channel`, etc.). Alternatively, add `/mission-control:resync <peer>` and
  `/mission-control:splashdown <peer>` as deterministic slash commands.

- **Operator-interjection between turns.** If Mission Control is awaiting peer
  and the operator types a new question to Mission Control, does FlightDirector
  hold the question until the peer responds, or route it immediately as a
  side-channel? Spec is silent.

### Caveats on the spec's own §"Open questions" 1–4

The spec's listed open questions:

1. **Hooks scope** — Recommend NO PostToolUse hook. Claude Code's native
   background-bash auto-notify is the trigger (subject to verification per
   reviewer question #1 above); layering a PostToolUse hook adds complexity
   without payoff.

2. **Peer-side state path** — `<peer-project>/thoughts/.mission-control-state.json`
   (single file, not directory) is sensible. Matches kimmy's `thoughts/`
   conventions.

3. **uuidgen fallback** — `uuidgen` works on both Mac (default) and Linux
   (`uuid-runtime` on Debian-likes). `/dev/urandom` fallback is reasonable
   insurance for minimal environments.

4. **jq dependency** — Declared + fail-open matches the orbital convention
   (the scaffolding plugin's `announce-setup.sh` follows the same pattern).
   Fine.
